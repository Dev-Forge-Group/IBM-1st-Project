# UniPlace 소유권 전환 준비

첫 시범 범위는 한 지역의 주거 호실이다. 담당자가 건물·호실과 소유주 계정의 관계를 증빙으로 확인한 뒤 공개와 신청을 연다. 기존 임대인 이름이나 전화번호로 계정을 자동 연결하지 않는다. 상세 권한과 API는 [계정과 자산 소유권 계약](account-ownership.md)에 따른다.

## 전환 전 확인할 항목

| 항목 | 확인 기준 |
| --- | --- |
| 운영 대상 | 환경, 데이터베이스, 현재 Flyway 버전, 앱 이미지의 커밋과 다이제스트, 적용·복구 담당자를 기록한다. 시작 기준은 V16이며, DB 기본 문자 정렬 규칙과 기존 `users.user_id`의 외래키 호환성을 확인한다. |
| 기존 자산 | 자산 ID별로 증빙 확인, 승인 대기, 보류를 구분한다. 시범 대상의 승인 담당자와 보류 사유를 정한다. |
| 기존 계정과 계약 | 기존 관리자에서 분류될 직원 계정과 활성 계약·입주자 관계를 점검한다. 과거 계약 당사자는 현재 자산 소유권과 별도로 검토한다. |
| 릴리스와 복구 | 동일 커밋의 필수 CI, 배포 차단, 복원 대상 DB와 이전 앱 이미지, 전환 중 쓰기 중단 방식 및 재개 기준을 확인한다. |

기존 매물은 자산 관계를 승인하기 전에도 공개 조회가 가능하다. 신규 방문 예약·계약·공용공간 예약은 해당 운영 소유주가 검증된 뒤 가능하다. 시범 대상의 승인과 사용자 안내를 먼저 준비한다. 기존 소비자의 계약 이력과 문서 접근은 계약 관계에 따라 유지한다.

## 격리 환경에서 연습하는 순서

1. MySQL 8.4에 V16까지 적용하고 기존 관리자·회원·입주자, 건물·호실, 계약 이력이 있는 합성 데이터를 준비한다. 계정과 자산의 ID, 기존 역할, 계약과 입주자 연결 및 Flyway 이력을 비교 기준으로 기록한다.
2. V16 스냅샷을 확보한 뒤 V17을 적용한다. 기존 관리자는 STAFF로, 나머지 기존 회원은 MEMBER로 분류되는지 확인한다. 기존 회원은 소비자 권한을 받고 소유주 자격, 자산 관리권, 과거 계약의 소유주 당사자 관계가 자동 생성되지 않아야 한다. 기존 역할 값과 자산·계약·입주자 이력은 보존한다.
3. V16 스냅샷을 별도 DB에 복원해 적용 전 이력과 데이터를 비교한다. 복원본에서 V17까지 다시 적용해 같은 소유권 전환 결과를 확인한다. 소요 시간과 불일치 여부를 기록한다.
4. 검증된 앱 이미지에서 직원 심사, 소유주 자산 관리, 소비자 읽기와 신청을 확인한다. 서로 다른 소유주 사이의 접근 거절, 기존 소비자의 계약 문서, 시범 범위 밖 자산의 조회 전용 상태도 확인한다.

저장소의 `V17OwnershipUpgradeIntegrationTest`는 1~3단계의 합성 MySQL 이관과 복원을 확인한다. 스냅샷에는 파일 메타데이터가 포함된다. 계약 PDF 등 파일 원본의 복원은 스토리지에서 별도로 확인한다. 4단계는 [권한 통합 테스트](ci.md)와 실제 스테이징 흐름에서 확인한다. 합성 환경의 결과와 운영 백업의 복원 가능성·복구 시간은 별도로 기록한다.

## 운영 진행과 중단 기준

전환 시점에는 승인된 쓰기 중단 계획에 따라 예약·계약 등 영향을 받는 쓰기를 멈춘다. 데이터 일치와 동일 커밋의 필수 검사, 시범 흐름이 확인되면 테스트된 경로로 쓰기를 재개한다. 시범 운영은 공개·방문 예약·계약 신청부터 시작하며 실제 계약 체결과 결제는 해당 운영 기준과 준비를 별도로 확인한다.

Flyway 실패, 이력 불일치, 의도하지 않은 권한 부여, 검증된 시범 매물의 신청 실패가 있으면 쓰기를 재개하기 전에 중단한다. MySQL의 DDL은 개별 단계에서 커밋될 수 있으므로 V17 전체가 자동으로 되돌아갈 것을 전제하지 않는다. 승인된 복구 계획에 따라 별도 DB에서 V16 백업과 이전 앱의 동작을 확인한 뒤 전환 경로를 결정한다. 이미 쓰기를 재개한 상태라면 새로 생긴 데이터의 대사와 보존 범위를 먼저 확정한다.

현재 저장소의 CI와 배포 workflow는 분리돼 있고, 배포 manifest의 백엔드 이미지는 `latest` 태그를 가리킨다. 운영 전에는 대상 커밋의 원격 필수 검사와 배포 대기가 실제 실패에 반응하는지, 실행 이미지의 다이제스트가 검증한 이미지와 일치하는지 확인한다. 클러스터 DB, 실제 소유권 증빙, 운영 스토리지와 기존 문서 URL은 해당 환경에서 별도로 확인한다.
