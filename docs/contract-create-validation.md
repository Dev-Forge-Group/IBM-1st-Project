# 계약 신청의 납부일·서명 검증

IBM-10은 `POST /contracts`의 납부일과 서명 입력을 저장 전에 확인한다. 기존 화면은 납부일을 1–31로 제한했지만 서버는 필수 여부만 검사해 0·32 같은 값을 저장했다. 이름이 있는 0바이트 서명은 필수 검사를 통과하고, 계약 저장·관리자 알림·Slack 이후 서명 업로드를 건너뛸 수 있었다.

## 입력과 실패 계약

| 입력 | 처리 |
| --- | --- |
| `paymentDay` | 필수 정수 1–31. DTO의 필수·범위 검사와 서비스의 범위 검사를 적용한다. 잘못된 숫자 형식·overflow는 기존 MVC binding의 400을 따른다. |
| `signFile` | 필수이며 내용이 있어야 한다. 파일명 유무와 관계없이 `isEmpty()`인 multipart 파일은 거절한다. |
| 인증·응답 | 기존 JWT 필터와 `currentUserId()`를 사용하며 기존 응답 형태를 유지한다. 입력 거절은 `400 / COMMON_400`이다. |
| 직접 서비스 호출 | null 요청·null/범위 밖 납부일·누락/빈 서명도 `BAD_REQUEST`로 거절한다. HTTP DTO 검사를 우회해도 같은 저장 경계가 적용된다. |

서비스는 현재 사용자를 확인한 뒤 두 입력을 검사하고 기간 검사·업무 조회·저장을 진행한다. 이 두 입력으로 거절한 요청은 계약·파일 행을 만들거나 storage·문서 생성·관리자 알림·Slack을 호출하지 않는다. HTTP의 누락 필드 메시지는 기존 필수 검사에 따르고, 여러 입력이 동시에 잘못된 요청의 첫 오류 메시지 순서를 고정하지 않는다.

정상 요청은 방의 금액, `requested` 상태, 서명 파일의 새 계약 연결, 문서 proxy URL과 기존 응답 필드를 사용한다. 기존 기간·겹침 검사와 REQUIRED 트랜잭션을 유지한다. 이미 저장된 납부일이나 entity 기본값을 일괄 변경하지 않으며, 31일을 해당 월말로 보정하는 청구 규칙도 별도 업무 계약이다.

## 화면과 복구

`ContractApply`는 0바이트 파일을 선택하면 미리보기를 읽기 전에 오류를 안내한다. 이전 정상 서명이 있으면 그 선택을 보존하고, 내용이 있는 파일을 다시 선택해 진행할 수 있다. 제출 시에도 서명이 비어 있는지 확인한다. 기존 납부일 1–31 검사와 서버 오류 표시·입력 보존·명시적 재시도를 연결한다.

## 검증 범위

`ContractCreateValidationIntegrationTest`는 실제 MySQL/Flyway·JWT·보안 필터·RANDOM_PORT HTTP와 실제 계약/파일 서비스를 사용한다. storage·문서 생성·외부 알림은 합성 fixture로 격리한다. 범위 밖·누락·형식 오류 납부일과 빈 서명의 거절, 직접 호출의 검증, 1·31 정상 경계, 기존 기간·겹침 오류를 확인한다. 실패 전후 계약·파일 행과 외부 효과가 같아야 한다. 이 suite는 [필수 CI](ci.md)에 포함한다.

화면 회귀는 빈 파일의 미리보기·제출 차단, 정상 선택 보존과 재선택, 오류 후 입력·재시도를 검사한다. opt-in 실제 브라우저 결과는 기본 CI와 별도 실행 증거로 기록한다. fixture는 합성 사용자·PNG만 사용하며 실제 고객 문서나 운영 storage를 조회하지 않는다.

이 보장은 납부일 범위와 필수 서명의 빈 내용에 대한 것이다. 서명 이미지의 실제 형식·확장자·용량, 문서 생성 실패 복구, 알림의 commit 시점과 계약 writer 동시성은 각자의 기존 정책을 따른다. 관리자 수정의 선택적 PDF 교체와 계약 유형별 가격 결정은 별도 경계다.
