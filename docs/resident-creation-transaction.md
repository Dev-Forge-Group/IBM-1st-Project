# 관리자 수동 입주자 등록의 트랜잭션

IBM-12는 `ResidentServiceImpl.createResident`의 쓰기 트랜잭션 선언을 명시한다. 기존 메서드는 클래스의 `@Transactional(readOnly = true)`를 물려받아, 새 입주자를 저장하는 관리자 HTTP 요청도 읽기 전용 연결에서 실행됐다. 기존 행을 읽어 반환하는 재요청만으로는 신규 저장의 실패를 확인할 수 없었다.

## 실행과 데이터 계약

| 호출 | 처리 |
| --- | --- |
| `POST /admin/residents` | 현재 DB 관리자 권한을 확인한 뒤 새 쓰기 트랜잭션에서 계약·회원·건물 매핑을 검사하고 등록한다. |
| 같은 계약·회원의 순차 재요청 | 이미 저장된 입주자의 동일한 ID와 기존 응답 필드를 반환한다. |
| 외부 쓰기 트랜잭션의 서비스 호출 | 기본 REQUIRED로 참여한다. 같은 트랜잭션의 미커밋 계약을 읽고, 입주자 등록도 외부 commit·rollback을 따른다. |
| 외부 읽기 전용 트랜잭션 | 기존 트랜잭션의 속성을 따른다. 쓰기 호출자는 적절한 쓰기 트랜잭션을 제공해야 한다. |
| `GET /admin/residents` | 클래스의 기존 readOnly 조회를 유지한다. |

입력은 기존 `buildingId`·`contractId`·`userId`이며 응답은 `residentId`와 이 세 필드다. 계약이 없으면 `CONTRACT_404`, 계약 소유 회원 또는 건물이 요청과 다르면 `COMMON_400`이다. HTTP 필수 입력·관리자 권한 검사는 기존 DTO와 보안 필터를 사용한다.

수동 등록은 계약 상태·방 점유·회원 역할·알림을 변경하지 않는다. 계약 활성화 시 자동 입주자를 생성하는 `ContractServiceImpl`의 기존 쓰기 경로는 별도의 업무 흐름이다. 기존 `uq_resident(contract_id, user_id)`와 FK를 사용한다. 순차 재요청의 기존 응답을 유지하는 범위이며, 경쟁 요청의 예외를 같은 응답으로 복구하는 동시 멱등 정책은 별도다.

## 실제 검증

`ResidentCreationTransactionIntegrationTest`는 실제 MySQL/Flyway·JWT·RANDOM_PORT HTTP와 실제 서비스·Repository를 사용한다. fixture만 명시적으로 commit하며 테스트 전체를 쓰기 트랜잭션으로 감싸지 않는다. 따라서 서비스가 테스트의 쓰기 트랜잭션에 합류해 읽기 전용 버그를 가리는 상황을 피한다.

관리자 신규 등록의 commit·후속 조회·순차 재요청과 기존 행 조회를 구분하고, 잘못된 매핑·입력·권한의 거절 전후 데이터를 확인한다. 외부 쓰기 트랜잭션에서는 새 미커밋 계약에 입주자를 등록하고, 독립된 raw JDBC 연결에서 두 행이 보이지 않는지 검사한다. 외부 rollback 뒤에도 등록과 계약이 남지 않아야 한다. 외부 연결을 확인할 때 트랜잭션에 묶인 연결을 재사용하지 않는다.

합성 사용자·계약과 별도 MySQL을 사용하며 실제 고객 데이터·storage·외부 알림을 조회하지 않는다. 이 suite는 [필수 CI](ci.md)에 포함한다. 이번 변경의 로컬 검증 범위는 백엔드이며, 프런트 동작·운영 배포·모든 계약 writer의 동시성 보장으로 확대하지 않는다.
