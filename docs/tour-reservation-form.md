# 투어 예약 화면의 조회 문맥

IBM-04는 `TourReservationCreate`의 건물·방·날짜 선택과 비동기 조회 결과를 연결한다. 날짜를 바꾼 뒤 새 시간을 기다리는 동안 이전 날짜의 시간으로 신청하거나, 늦게 도착한 과거 조회가 현재 결과·오류·로딩 상태를 덮는 경로를 수선한다. 인라인 팝업과 독립 페이지가 같은 규칙을 사용한다.

## 조회와 선택

- 방 목록은 조회한 건물 ID와 함께 보관하고 현재 건물에 속하는 결과만 사용한다. 선택한 방이 현재 목록에 실제로 존재해야 시간 조회와 신청에 쓸 수 있다. 건물 변경 중 이전 건물의 방 ID를 새 건물과 조합하지 않는다.
- 시간 목록과 선택은 건물·검증된 방·날짜의 조합에 속한다. 문맥이 바뀌면 이전 목록과 선택은 신청 근거가 될 수 없고 확인창도 닫는다. 새 조회가 끝나면 현재 목록에서 다시 시간을 선택해야 한다.
- 각 방·시간 조회는 해당 요청이 여전히 유효할 때만 성공 결과, 오류와 로딩 종료를 반영한다. 이전 요청의 성공이 새 결과를 덮거나, 이전 실패·완료가 현재 목록과 진행 상태를 지우지 않는다. 방을 비우거나 날짜를 지웠을 때도 이전 요청의 반영 권한이 끝난다.
- 서버가 반환한 시간 중 시작과 종료 날짜가 모두 현재 선택 날짜인 항목을 사용한다. 현재 문맥의 시간 목록에 포함된 선택만 신청할 수 있다.

AI 초기 추천은 초기 건물·방 ID가 제공되면 그 ID가 일치하고, 추천 시작 날짜가 현재 날짜이며, 현재 가용 시간의 시작과 제공된 종료 시각이 맞을 때 자동 선택한다. 일치한 추천은 한 번만 적용한다. 날짜·방을 변경할 때 적용 여부를 초기화하여 과거 추천을 다시 선택하지 않는다.

## 신청과 서버 계약

방·시간을 조회 중이거나 현재 문맥의 유효한 선택이 없으면 신청을 허용하지 않는다. 확인창에서 신청을 확정할 때도 같은 조건을 다시 검사하고, 진행 중인 중복 제출을 막는다. POST에는 현재 건물 ID, 그 건물의 확인된 방 ID와 선택한 날짜의 시작·종료 시각을 보낸다.

예약자 이름·전화·PIN은 기존 필드와 검증을 사용한다. 전화 원문과 숫자 4자리 PIN을 기존 API payload에 전달하며, [전화 표기 호환](tour-telephone-compatibility.md)은 서버 계약을 따른다. 성공한 독립 페이지는 기존 예약 조회 경로로 이동하고 인라인 모드는 기존 `onSuccess`를 호출한다.

가용 시간 조회와 화면의 문맥 검사는 생성 성공을 보장하지 않는다. 다른 요청이 먼저 예약하면 [V16의 서버 쓰기 검사](tour-reservation-concurrency.md)가 최종 충돌을 판단한다. 화면에서 문맥을 바꾸는 것은 이미 전송한 생성 요청을 회수하는 동작이 아니며, 이번 변경은 생성 API의 멱등성 키·자동 재시도 계약을 추가하지 않는다.

공개 호실의 소유 관계가 아직 확인되지 않았거나 호실 상태가 예약 불가이면 슬롯 응답은 빈 `availableSlots`와 함께 `unavailableReason`을 반환한다. 방문 예약 화면은 이 사유를 표시한다. 신청 시 서버가 현재 조건을 다시 확인하며, 검증된 운영자가 없으면 `400 TOUR_RSV_400_7`, 호실 상태로 예약할 수 없으면 `400 TOUR_RSV_400_3`을 반환한다. 이미 접수된 예약의 조회·취소에는 기존 예약 정보가 사용된다.

## 검증

IBM-07은 생성 실패 메시지를 팝업과 독립 페이지 모두에 한 번 표시한다. 실패한 요청에서 입력·현재 선택을 보존하고 성공 이동/callback을 실행하지 않는다. 사용자가 다시 확인한 현재 선택으로 재시도할 수 있으며 자동 POST 재시도나 서버 멱등성은 추가하지 않는다. [실제 HTTP 흐름·브라우저 검증](tour-http-journey.md)은 mock 화면 회귀와 구분한다.

`TourReservationCreate.test.jsx`는 React Testing Library와 지연시킨 mock API 응답으로 인라인·독립 페이지의 날짜 변경, 과거 성공·실패·완료의 역순 도착, 방 선택 해제, 건물 변경 시 방 소속 검증, 최초 AI 추천과 뒤늦은 과거 추천을 검사한다. 현재 문맥의 payload와 기존 전화·PIN 전달도 확인한다.

수정 전 같은 11개 회귀 중 10개가 실패하고 대조 1개가 통과했으며, 수정 후 집중 검사 11개가 통과했다. 이 결과는 mock API 기반 화면 회귀다. 전체 프런트엔드 검사·실제 서버 통합·원격 Actions·운영 배포 결과는 각각의 실행 증거로 확인한다.
